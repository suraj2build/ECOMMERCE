What remains open — read this precisely

The blocked discounted exchange (EXC-2026-000002) remains unverified through payment and completion. Its replacement priced the same as the original at catalogue rate, but the order's own ₹200 coupon had reduced the original line's frozen value below the replacement's full catalogue price — so the exchange service correctly computed a CUSTOMER_PAYS settlement of ₹200, not EVEN. Collecting that difference goes through the real Razorpay payment provider; this codebase has no mock Razorpay implementation the way it has a MOCK shipping carrier, and no Razorpay test credentials are configured in this isolated stack, so the payment correctly failed safe with no network call and no fabricated success.

The second order (EXC-2026-000003) proves the EVEN-settlement path only — it does not replace the missing payment test. It is a different order, with a different settlement direction, exercising a different code path (no payment collection step at all). Whether a CUSTOMER_PAYS exchange can actually collect its price difference and reach COMPLETED is still an open question, to be answered by a real Razorpay sandbox run, not inferred from this result.

Setup notes

What this run needed that the demo catalogue doesn't ship with by default — none of it a product defect, all of it legitimate operator configuration:

  • A serviceable PIN code (110011) and a warehouse return address, both set via the real staff API — a fresh database has neither, and a real launch would configure both before taking orders.
  • 150 loyalty points and ₹150 store credit granted to the test customer directly — via the real /loyalty/adjust staff route for points, and a direct ledger entry for credit (account.spec.ts uses the same method; no staff store-credit-issuance route exists in this codebase to exercise instead).
  • A coupon (WALKTHRU200, ₹200 flat, compatible with loyalty and store credit) created via the real staff promotions API.
